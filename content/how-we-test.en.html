FileMoss tools are meant to process a file on your device. This page names the open-source libraries that do that work, describes the automated checks we run, and shows how to confirm in your browser that the file itself is not uploaded.

Libraries that run in the tab

The code for each tool is served from FileMoss and executed locally. These are the main libraries and the job each one does:

  • pdf-lib creates and edits PDFs: merge, split, rotate, delete pages, JPG to PDF, compress, page numbers, watermarks, and the PDF output from the document scanner. @pdf-lib/fontkit embeds a subset of Noto Sans, and Noto Sans JP when the text needs it, for page numbers and text watermarks.
  • Mozilla's PDF.js reads and renders PDF pages for PDF to JPG, PDF to Word, and PDF to Excel.
  • JSZip writes the .docx from PDF to Word, and builds ZIP downloads when a tool gives you more than one file.
  • SheetJS (the xlsx library) reads and writes Excel workbooks for CSV to Excel, merged or de-duplicated spreadsheets, and PDF to Excel.
  • qpdf-wasm, a WebAssembly build of qpdf, powers Unlock PDF. It makes one attempt with the password you type, or writes a copy without owner restrictions when the file is already readable. It does not try other passwords.
  • Tesseract.js does on-device OCR for Image to Text and the document scanner. Language data is served from FileMoss, not from a third-party host at click time.
  • heic2any decodes HEIC photos, including on the HEIC to JPG page. qrcode-generator draws QR codes. Image resize, compress, and format conversion use the browser Canvas API. Unlock PDF and OCR also depend on WebAssembly.

Files themselves are read with the browser File API. They are not attached to a form that posts the document to a server.

Automated checks

The FileMoss repository has a test runner (test_all.sh) and focused scripts we use when something changes. Not every tool is covered the same way, but the checks are real and they live next to the code:

  • tests/test_core.js covers shared text and date helpers: word counts, case conversion, diffs (including Vietnamese diacritics in NFC and NFD form), and related utilities.
  • tests/test_browser.js drives a real Chrome window against sample files for many tools, including merge, split, rotate, delete pages, JPG to PDF, PDF to JPG, image compress and resize, CSV conversion, QR codes, and the calculators and text tools in that script.
  • Separate browser scripts cover PDF compression, the document scanner, Vietnamese OCR, and PDF to Word (the last also checks the .docx in Python, including stored fixtures). Newer PDF and spreadsheet tools (page numbers, watermarks, unlock, merge CSV, remove duplicate rows) have their own acceptance script.

We run those checks after editing a tool, updating a shipped library, or changing shared helpers. That is not a claim that a test has run on every deploy, and a green run does not guarantee that your particular file will convert cleanly. Odd PDFs, huge images, and hard-to-read scans still fail. If one does, use the Contact page.

Confirm that your file is not uploaded

You can check this yourself in the browser's Network panel. Chrome's docs are here: Chrome DevTools, Network tab. Firefox and Edge have an equivalent.

  1. Open the FileMoss tool you want to try and wait until the page has finished loading.
  2. Open DevTools (in Chrome, F12 or right-click and choose Inspect) and switch to the Network tab. Turn on "Preserve log" so a later navigation does not wipe the list.
  3. Choose a file, run the tool, and download the result if the tool offers one.
  4. Look at the requests that appeared after you chose the file. You should not see a request whose payload is the PDF, image, or spreadsheet itself: no multi-megabyte POST, and no multipart upload of the document.
  5. You will usually see one or more small POST requests to /api/e. Click one and read the request body. It is a short JSON object such as {"t":"merge-pdf","a":"upload","l":"en"}. t is the tool's URL slug, a is the action (upload when a file is chosen, process_done when work finishes, download or copy when you take the result, calc on calculator pages), and l is the page language. The body does not include a filename, file bytes, or the text you typed. The server rejects a body larger than 300 bytes.
  6. After the page and its libraries have loaded, you can go offline and still process a file already on the device. The /api/e call will fail quietly; your file still never leaves the browser. If you have not yet used a tool that lazy-loads an extra library (for example, the first time you open Unlock PDF or Image to Text), that library file has to be fetched first. That download is our script or WebAssembly module, not your document.

The privacy policy describes what else is stored with a usage event: the date (not the time of day), the country Cloudflare reports, and a browser family such as Chrome. No cookie is set for this, and we do not keep your IP address. A short-lived, salted hash of the address is used only to blunt abuse, then discarded.

How we handle a bug

If a tool mangles a file or a number looks wrong, use the Contact page. A description of the file (page count, language, whether it is scanned or password-protected) is more useful than a vague "it failed." Do not send confidential documents unless you have removed anything sensitive and are willing to share them. We try to reproduce the failure, fix the tool or document a genuine limit (for example, a scanned PDF with no text layer), and add a check when that keeps the fix in place.
